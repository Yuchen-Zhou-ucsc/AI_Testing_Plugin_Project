## 2. Bug 描述

产品需求规定用户名长度必须不少于6个字符。当用户提交长度少于6个字符的用户名时，系统应拒绝注册并返回 HTTP 400。

在自动化测试中，系统使用4个字符的用户名 `r5x2` 调用注册接口。接口没有拒绝该请求，而是返回注册成功和 HTTP 201。

后续注册页 UI 自动化测试也复现了同一问题：Playwright 在真实浏览器中输入运行时随机生成的5位用户名和有效密码后，系统仍然返回 HTTP 201，并按注册成功流程处理。本次 Playwright 控制台输出记录了预期状态码、实际状态码和测试状态，但没有保存该随机用户名的具体值。

该实际行为与需求 `REG-002` 不一致，说明注册接口缺少用户名最小长度校验。问题根因位于后端业务校验，不是前端展示或测试脚本误判。

## 6. 预期结果

用户名 `r5x2` 只有4个字符，不符合用户名长度不少于6个字符的要求。

系统应：

* 拒绝注册；
* 返回 HTTP 400；
* 不在数据库中创建该用户。

## 7. 实际结果

系统接受了注册请求并返回 HTTP 201。

实际响应为：

```json
{
  "message": "Registration successful",
  "status": "success"
}
```

自动测试结果为：

| 项目    | 结果   |
| ----- | ---- |
| 预期状态码 | 400  |
| 实际状态码 | 201  |
| 测试状态  | Fail |

UI 自动化复现结果为：

| 项目 | 结果 |
| --- | --- |
| UI 测试编号 | REG-002 |
| 预期状态码 | 400 |
| 实际状态码 | 201 |
| 页面行为 | 按注册成功流程处理 |

自动测试执行器在该用例结束后清理了本次测试成功创建的临时账号。临时账号是否被清理不影响 Bug 结论，因为注册接口已经错误地接受了不符合长度要求的用户名。

## 8. 影响分析

该问题可能造成以下影响：

1. 用户可以注册不符合产品规则的短用户名。
2. 注册接口的实际行为与 PRD 和需求规格说明书不一致。
3. 如果不使用测试账号清理功能，实际业务中可能保存不符合规则的用户数据。
4. 前端页面注册流程会把短用户名当作成功注册处理，用户体验和产品规则不一致。
5. 后续功能可能需要额外处理不符合规则的历史用户名。

由于该问题会违反明确的业务规则，但不会导致系统崩溃、数据泄露或服务完全不可用，因此严重程度记录为 Medium。

## 9. 原因分析

GitHub 当前代码中的注册函数会检查：

* 请求体是否为 JSON；
* 用户名和密码是否为空；
* 用户名是否重复。

但是在保存用户之前，没有执行用户名长度是否达到6个字符的检查。

相关代码位置：

```text
backend/app.py
register()
```

代码中明确保留了“故意不检查用户名是否达到6位”的逻辑，用于本项目的自动化测试原型演示。因此，该问题是已知且有意保留的业务规则 Bug。

Playwright UI 自动化失败只是从浏览器页面操作路径再次暴露同一后端校验缺失，并不代表需要单独修复前端页面逻辑。

## 10. 修复建议

当前 MVP 演示阶段不修复该问题。若系统进入实际开发或发布阶段，建议：

1. 在 Flask 注册接口中增加用户名最小长度校验。
2. 当用户名少于6个字符时，返回 HTTP 400。
3. 在前端注册表单中增加相同的长度提示，以改善用户体验。
4. 后端校验必须保留，不能只依赖前端校验。
5. 修复后重新执行 TC-004 及完整注册测试用例。

## 11. 修复验收标准

修复后应满足：

1. 用户名少于6个字符时，注册接口返回 HTTP 400。
2. 不符合长度要求的用户名不会写入数据库。
3. 用户名刚好为6个字符且其他输入有效时，注册成功并返回 HTTP 201。
4. 用户名超过6个字符且其他输入有效时，注册成功并返回 HTTP 201。
5. 空用户名或空密码仍然返回 HTTP 400。
6. 重复用户名仍然返回 HTTP 409。
7. TC-004 的执行状态由 Fail 变为 Pass。
8. 其他原有注册测试用例仍然通过。
