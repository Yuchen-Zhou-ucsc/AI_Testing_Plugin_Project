## 2. 项目背景

本项目旨在验证 AI 驱动的软件自动化测试流程是否可行。目标流程包括需求输入、需求分析、测试用例生成、测试执行、结果判断、测试报告整理和 Bug 记录。

由于项目无法直接接入公司内部系统，因此使用 React、Flask 和 SQLite 开发一个独立的登录注册 Demo，作为 AI 自动化测试插件的测试对象。

Demo 中保留一项已知的业务规则问题：产品需求规定用户名长度不得少于 6 个字符，但注册接口未执行该长度校验。该问题用于验证 AI 能否根据需求生成测试用例、执行测试并发现预期结果与实际结果不一致的情况。在原型验证完成前，不修复该问题。

## 3. 产品目标

本项目需要实现以下目标：

1. 建立一个可以独立运行的注册和登录 Demo。
2. 使用 SQLite 保存用户账号信息。
3. 使用密码哈希方式保存密码，避免在数据库中存储明文密码。
4. 接收用户输入的自然语言产品需求。
5. 使用 AI 根据需求生成结构化测试用例。
6. 自动执行注册接口测试。
7. 对比预期状态码和实际状态码，并显示 Pass 或 Fail。
8. 通过测试发现预先保留的用户名长度校验问题。
9. 使用项目文档记录需求、测试用例、测试结果和 Bug 信息。

## 4. 目标用户

### 4.1 测试人员或产品人员

输入产品需求，查看 AI 生成的测试用例，执行测试并检查测试结果。

### 4.2 Demo 系统用户

使用注册页面创建账号，并使用正确的用户名和密码登录系统。

### 4.3 项目评审人员

查看项目代码、运行效果和配套文档，了解 AI 自动化测试流程的实现方式和验证结果。

## 5. 产品范围

### 5.1 本版本包含的功能

* 用户注册
* 用户登录
* SQLite 用户数据存储
* 重复用户名检查
* 用户名和密码非空检查
* 密码哈希存储与验证

## 6. 用户使用流程

### 6.1 注册和登录流程

1. 用户进入注册页面。
2. 用户输入用户名和密码。
3. 前端将注册信息发送至 Flask 后端。
4. 后端检查用户名和密码是否为空，并检查用户名是否重复。
5. 注册成功后，系统将用户名和密码哈希值保存到 SQLite 数据库。
6. 用户进入登录页面并输入账号信息。
7. 后端验证用户名和密码。
8. 验证成功后，用户进入欢迎页面；验证失败时，系统返回错误提示。

### 6.2 AI 自动化测试流程

1. 测试人员进入 AI 测试页面。
2. 测试人员输入一条产品需求。
3. 系统调用 AI 接口生成 5 条结构化测试用例。
4. 测试人员在页面中检查生成的测试场景、步骤、数据和预期结果。
5. 测试人员点击“执行测试”。
6. 后端依次调用注册接口执行测试。
7. 系统记录每条用例的预期状态码和实际状态码。
8. 系统根据两个状态码是否一致，将结果标记为 Pass 或 Fail。
9. 测试人员根据真实执行结果整理测试报告和 Bug 单。

## 7. 功能需求

### 7.1 用户注册需求

| 需求编号    | 功能需求            | 预期行为                            |
| ------- | --------------- | ------------------------------- |
| REG-001 | 用户名不能为空         | 用户名为空时拒绝注册，返回 HTTP 400          |
| REG-002 | 用户名长度不得少于 6 个字符 | 用户名少于 6 个字符时拒绝注册，返回 HTTP 400    |
| REG-003 | 密码不能为空          | 密码为空时拒绝注册，返回 HTTP 400           |
| REG-004 | 用户名不能重复         | 用户名已存在时拒绝注册，返回 HTTP 409         |
| REG-005 | 有效账号可以注册        | 输入符合要求且用户名未被使用时注册成功，返回 HTTP 201 |
| REG-006 | 密码不得以明文保存       | 系统应将密码转换为哈希值后再保存到数据库            |

其中 REG-002 是本项目用于验证自动化测试能力的重点需求。当前代码有意未实现该校验，用于观察测试系统能否发现实际行为与产品需求不一致。

### 7.2 用户登录需求

| 需求编号      | 功能需求        | 预期行为                    |
| --------- | ----------- | ----------------------- |
| LOGIN-001 | 用户名和密码不能为空  | 任一字段为空时拒绝登录，返回 HTTP 400 |
| LOGIN-002 | 正确账号和密码可以登录 | 验证成功后返回 HTTP 200        |
| LOGIN-003 | 错误密码不能登录    | 返回 HTTP 401，并且不允许进入欢迎页面 |
| LOGIN-004 | 不存在的用户名不能登录 | 返回 HTTP 401，并且不泄露账号是否存在 |
| LOGIN-005 | 密码使用哈希方式验证  | 登录时使用密码哈希验证，不直接比较明文密码   |

### 7.3 AI 测试用例生成需求

| 需求编号   | 功能需求        | 预期行为                                               |
| ------ | ----------- | -------------------------------------------------- |
| AI-001 | 支持输入自然语言需求  | 用户可以在页面中输入中文产品需求                                   |
| AI-002 | 需求不能为空      | 空需求不得提交给 AI 生成测试用例                                 |
| AI-003 | 自动生成测试用例    | 每次生成 5 条中文结构化测试用例                                  |
| AI-004 | 覆盖不同测试场景    | 测试用例应包含正常、边界和异常情况                                  |
| AI-005 | 输出固定结构      | 每条用例应包含编号、场景、前置条件、步骤、测试数据、预期结果、接口方法、接口地址、请求体和预期状态码 |
| AI-006 | 提供可执行测试数据   | 请求体中的用户名和密码必须可以直接用于接口测试                            |
| AI-007 | 生成结果可以在前端查看 | 页面应以表格形式展示生成的测试用例                                  |

### 7.4 自动化测试执行需求

| 需求编号     | 功能需求      | 预期行为                              |
| -------- | --------- | --------------------------------- |
| TEST-001 | 自动执行测试用例  | 系统按照测试用例中的请求信息调用注册接口              |
| TEST-002 | 限制允许执行的接口 | 当前版本只允许执行 `POST /api/register`    |
| TEST-003 | 支持重复用户名场景 | 系统应自动建立重复用户名测试所需的前置账号             |
| TEST-004 | 记录实际响应    | 系统应记录实际 HTTP 状态码和实际响应内容           |
| TEST-005 | 自动判断测试状态  | 预期状态码与实际状态码一致时标记为 Pass，否则标记为 Fail |
| TEST-006 | 展示执行结果    | 前端应展示预期状态码、实际状态码和测试状态             |
| TEST-007 | 清理成功注册的测试账号 | 当测试返回 HTTP 201，且该用户名在测试前不存在时，系统应在执行后删除该账号 |

## 8. 业务规则

1. 用户名和密码都是注册必填字段。
2. 用户名长度必须大于或等于 6 个字符。
3. 每个用户名在数据库中必须唯一。
4. 密码必须经过哈希处理后再保存。
5. 登录时必须验证用户名和密码。
6. AI 每次生成 5 条测试用例。
7. 测试用例应覆盖正常、边界和异常情况。
8. 当前自动执行功能仅允许测试注册接口。
9. 测试结果必须根据真实接口响应生成，不能由人工预先填写。
10. 用户名长度校验问题在原型验证阶段必须保留，不能提前修复。

## 9. 非功能需求与项目约束

### 9.1 安全要求

* OpenAI API Key 必须存放在 `backend/.env` 中。
* `.env` 文件不得上传到 GitHub。
* 用户密码必须以哈希形式存储。
* 测试执行器不得调用当前原型范围外的未知接口。

### 9.2 数据要求

* 用户数据使用 SQLite 保存。
* 数据库文件 `users.db` 不上传到 GitHub。
* 正常重启前后端服务时，数据库中的正式注册数据应继续保留。
* 对于测试中注册成功且测试前不存在的临时账号，系统应在执行后进行清理。

### 9.3 技术约束

* 前端使用 React、Vite、Axios、React Router 和 Ant Design。
* 后端使用 Python、Flask、Flask-CORS 和 SQLite。
* AI 用例生成使用 OpenAI Responses API 和 Pydantic 结构化输出。
* 当前项目在本地开发环境中运行，不作为生产系统使用。

## 10. 验收标准

项目达到以下条件时，可以认为 MVP 核心目标已经实现：

1. React 和 Flask 前后端能够正常启动。
2. 用户能够通过页面完成注册和登录。
3. 用户信息能够保存到 SQLite 数据库。
4. 数据库中的密码以哈希值形式保存。
5. 页面能够接收自然语言产品需求。
6. AI 能够返回 5 条结构化中文测试用例。
7. 系统能够自动执行注册接口测试。
8. 页面能够显示预期状态码、实际状态码和 Pass/Fail。
9. 测试系统能够识别用户名长度需求与接口实际行为之间的不一致。
10. GitHub 仓库中包含源代码、README 和必要的产品测试文档。

实际测试数量、测试输入、通过数量、失败数量和通过率不在本 PRD 中填写，统一以之后的真实测试执行记录和测试报告为准。
