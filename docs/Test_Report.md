## 2. 测试目的

本次测试用于验证 AI 自动化测试插件原型能否完成以下流程：

1. 接收自然语言产品需求。
2. 使用 AI 生成结构化测试用例。
3. 自动执行注册接口测试。
4. 记录预期状态码和实际状态码。
5. 自动判断每条用例为 Pass 或 Fail。
6. 发现产品需求与接口实际行为之间的不一致。
7. 通过 Playwright 注册页 UI 自动化，从真实浏览器操作路径复现同一业务规则问题。

本次测试的重点是验证需求 `REG-002`：用户名长度必须不少于6个字符。注册接口代码中有意未实现该长度校验，用于验证插件能否发现预埋的业务规则 Bug。

## 3. 测试需求

本次输入插件的产品需求为：

> 用户注册时，用户名和密码均为必填项。用户名长度必须不少于6个字符，并且不能与已有用户名重复。用户名或密码为空、用户名少于6个字符时，系统应拒绝注册并返回HTTP 400；用户名重复时应返回HTTP 409；当用户名长度不少于6个字符、密码非空且用户名未被使用时，系统应注册成功并返回HTTP 201。

## 5. 测试环境与执行方式

| 项目     | 内容                                       |
| ------ | ---------------------------------------- |
| 运行环境   | 本地开发环境                                   |
| 前端     | React + Vite，运行于 `http://localhost:5173` |
| 后端     | Flask，运行于 `http://127.0.0.1:5000`        |
| 数据库    | SQLite                                   |
| 手工测试浏览器 | Google Chrome                            |
| UI 自动化浏览器 | Chromium                                 |
| 用例生成接口 | `POST /api/ai/generate-tests`            |
| 接口测试执行接口 | `POST /api/tests/execute`                |
| UI 测试执行接口 | `POST /api/ui-tests/execute`             |
| 被测试接口  | `POST /api/register`                     |
| UI 自动化工具 | Playwright + Chromium                    |

AI 生成的5条测试用例通过自动执行接口提交。后端使用 Flask 测试客户端逐条调用真实注册接口，并记录实际响应。系统通过比较预期状态码和实际状态码生成 Pass 或 Fail 结果。

注册页 UI 自动化测试通过 Flask 后端触发项目内固定的 Playwright 用例。Playwright 启动 Chromium，打开注册页面，自动输入用户名和密码并点击注册按钮。后端读取 Playwright JSON 报告后，将每条 UI 用例转换为 Pass、Fail 或 Error，并返回给前端页面展示。

本报告中的接口测试数据以 `docs/Test_Cases.xlsx` 中保存的真实执行记录为准，并在 2026-09-08 通过 `/api/tests/execute` 复核，复核结果仍为4条 Pass、1条 Fail。UI 自动化结果以 2026-09-08 本地 `npm run test:ui` 输出为准。UI 用例中的注册用户名由脚本运行时随机生成；本次控制台输出记录了预期状态码、实际状态码和 Pass/Fail，但没有保存随机用户名的具体值，因此本文档不编造该随机用户名。

## 8. 失败用例分析

### 8.1 TC-004：用户名最小长度校验失败

测试输入：

```text
username: r5x2
password: Yp6$kL9@vN
```

预期行为：

* 用户名只有4个字符，不符合“用户名长度不少于6个字符”的要求。
* 系统应拒绝注册。
* 预期 HTTP 状态码为400。

实际行为：

* 系统接受了注册请求。
* 实际 HTTP 状态码为201。
* 实际响应为：

```json
{
  "message": "Registration successful",
  "status": "success"
}
```

测试结论：

* 预期状态码400与实际状态码201不一致。
* TC-004 被自动标记为 Fail。
* 该结果证明注册接口没有执行用户名最小长度校验。
* 该问题与项目中预先保留的 `REG-002` Bug 一致。

### 8.2 UI REG-002：短用户名在页面注册流程中被错误接受

UI 自动化测试通过真实浏览器打开注册页面，输入运行时随机生成的5位用户名和有效密码，并点击注册按钮。本次 Playwright 控制台输出未保存该随机用户名的具体值。

预期行为：

* 前端提交注册请求后，后端应拒绝该短用户名。
* 预期 HTTP 状态码为400。
* 页面不应将该用户当作注册成功处理。

实际行为：

* 后端返回 HTTP 201。
* 页面按注册成功流程跳转。
* UI 自动化用例 `REG-002` 被标记为 Fail。

测试结论：

* UI 自动化复现了与接口测试相同的用户名长度校验缺陷。
* 该问题不是页面展示误差，而是注册接口业务规则缺失导致的真实产品行为问题。

## 10. 风险与测试限制

1. 当前自动执行器只支持 `POST /api/register`，不能根据同一份需求测试登录或其他接口。
2. AI 固定生成5条测试用例，因此本次将用户名为空和密码为空合并在同一条用例中，没有分别执行两个独立输入场景。
3. 本次测试仅在本地开发环境中执行，不能代表生产环境运行结果。
4. 本次仅执行注册页 UI 自动化，尚未覆盖登录页、欢迎页、多浏览器兼容性、性能和安全测试。
5. AI 生成的测试数据可能在不同调用中变化，因此本报告只对应2026年8月13日生成并执行的这一组测试用例。
6. `REG-002` Bug 在当前原型中有意保留。如果系统用于实际业务，该问题会导致不符合规则的用户名被接受。

## 11. 测试结论

本次共执行5条注册接口测试用例，其中4条通过、1条失败，通过率为80%，执行过程中没有出现 Error。

同时，本项目补充执行了5条注册页 UI 自动化用例，其中4条通过、1条失败，通过率为80%，执行过程中没有出现 Error。

自动化测试成功发现了用户名最小长度未校验的问题。该结果证明当前原型已经能够完成“需求输入 → AI生成测试用例 → 自动执行 → 预期与实际结果比较 → 发现Bug”的核心测试流程，并且可以通过 Playwright 从真实浏览器页面操作路径复现同一缺陷。

从原型验证角度看，本次测试达到预期目的，项目可以用于展示 AI 自动化测试闭环。从实际产品发布角度看，系统当前不适合投入生产使用；在实际发布前必须修复 `REG-002`，并补充登录、密码安全、多页面 UI 自动化、性能和安全测试。
